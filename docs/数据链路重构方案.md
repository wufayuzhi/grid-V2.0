## 一、三大块落地设计

### 模块 A：OKX WebSocket 长链接（行情/K线实时推送）

**目标**：把「前端每秒1次HTTP轮询 → 后端每次实时调OKX」改为「后端连OKX WS 实时推 → 后端缓存 → 前端读缓存」。

**新增文件**：`engine/ws_market.py`（WS 客户端，单例，随主进程常驻）

**订阅频道**（OKX 公共频道，仅只读订阅，绝不下单）：

| 数据 | WS 频道 | 缓存落点 |
|:--|:--|:--|
| K线 | `candle<bar>`（按当前 tf 订阅）| `_candle_cache` |
| 行情(tickers) | `tickers` | `_ticker_cache` |
| 指数价格 | `index-tickers` | `idxPx` |
| 标记价格 | `mark-price` | `mark_px` |
| OI 未平仓 | `open-interest` | `_oi_cache` |

**接入点**：`data_loop`（tick.py）启动时拉起 WS 客户端；WS 每次推送直接更新缓存，**替换掉原来的 REST 刷新**（`refresh_ticker`/`fetch_oi`）。

**关键机制**：
1. **断线自动重连**：指数退避（1s→2s→4s…上限30s），重连后自动重新订阅全部频道。
2. **心跳**：`ping_interval=20s`（websockets 库内置）。
3. **切币重订阅**：监听 `st.inst_id` 变化 → 退订旧 instId、订阅新 instId（candle/tickers/OI 全重订）。
4. **WS + 低频REST 并线（用户2026-08-19确认）**：WS 实时推送(主,毫秒级) + 低频 REST 轮询(辅,每5秒) **同时运行**，两者数据**都写进同一缓存、按时间戳并线取最新**。WS 断线/漏推时 REST 兜底自动补上，缓存始终新鲜不中断。**不是**"断线才降级"，而是双通道常驻冗余。
5. **多 tf**：前端当前用哪个 tf，就订阅哪个 candle 频道（后端按需切换）。
6. **交易用价**：始终取缓存中「最近一次校验通过」的值 + 时间戳校验 + stale 标记；超过阈值标"降级中"，前端提示，绝不用陈旧脏价下单。

**改动的既有文件**：
- `engine/tick.py`：data_loop 接入 WS 启动/重连，行情刷新改走缓存
- `data/ticker.py`：`apply_ticker` 增加「从 WS 推送更新」入口（复用现有解析/落 state 逻辑）；`refresh_ticker`/`fetch_oi` 保留作 fallback
- `data/candle.py`（若存在）或 K 线获取：WS 推的 K 线写缓存，供 `/api/v1/candles` 读

### 模块 B：账单三层保障（不漏记 + 不限流）

**目标**：调平记录「实时不漏」，同时把账单翻页频率从「每次打开页面」降到「5分钟一次」。

| 层 | 机制 | 文件 |
|:--|:--|:--|
| **①实时层** | 引擎成交/调平时**立即 append 记录**到 `st.adjust_records` | `engine/grid.py`（成交回调）、`engine/adjust.py` |
| **②对账层** | 账单 5 分钟低频重建（已有 `_BILLS_REFRESH_INTERVAL=300s`）补漏/纠错/算准手续费张数 | `engine/tick.py` |
| **③撤销层** | 订单历史识别撤销单，5分钟低频并入（`_merge_canceled_records`）| `engine/tick.py` 低频任务 |

**关键改动**：
1. `engine/tick.py` 5分钟账单任务：`calc_bills_stats` 后**追加** `_merge_canceled_records`（撤销单低频维护，不再只在接口里做）。
2. `api/routes.py` `adjust-history` 接口：**删除内部翻页**（`calc_bills_stats` + `_merge_canceled_records`），改为**只读 `_serialize_adjust(st)`** 缓存。前端永不触发翻页。
3. 三层去重：复用现成 `(ts, group)` 幂等逻辑，成交记录与账单重建不重复。

**效果**：调平记录引擎成交即写（零空窗）→ 不漏；账单翻页从「每次打开」降到「5分钟1次」→ 429 根治；数据滞后最多 5 分钟（B 方案用户已接受）。

### 模块 C：统一缓存层（前端全打本地缓存）

**目标**：前端所有请求只打后端内存缓存，秒回，不再让 OKX 参与每次前端请求。

**设计**：
- 后端维护统一内存缓存：`_ticker_cache` / `_mark_px` / `_oi_cache` / `_candle_cache` / `state`。
- WS（模块A）+ tick 主循环（低频账单/账户同步）共同维护缓存新鲜度。
- 前端所有数据接口（market/trend/balance/pending/adjust/bootstrap）都从缓存读，live 调用（balance/precheck/pending）包超时+降级（bootstrap 已实现）。

**改动**：主要是后端缓存读取路径统一；前端改造点在「轮询时序」（见模块A遗漏7）。

## 二、数据流（改造后）

```
OKX WS 公共频道 ──推──▶ 后端 WS 客户端(engine/ws_market) ──写──▶ 内存缓存
                                                                ▲
tick 主循环(低频: 账户/账单/撤销单/趋势/ATR) ────────────────▶ 内存缓存
                                                                │
前端(每1~3s轮询或bootstrap) ──读──▶ 后端API ──读──▶ 内存缓存(秒回)
```

- 实时行情/K线：WS 推 → 缓存 → 前端读（毫秒级新鲜，不打OKX）
- 账户/持仓/余额/趋势/调平记录：低频任务 → 缓存 → 前端读（秒回，OKX 调用极低）
- 交易决策（风控/网格触发）：**仍读后端 state 里的真实标记价/持仓**，与展示缓存解耦，不受 WS 抖动影响

## 三、连锁影响审计表

### 模块 A（WS）连锁影响

| 改动点 | 下游消费方 | 影响 | 结论 |
|:--|:--|:--|:--|
| 行情来源 REST→WS | 前端行情/顶栏/K线显示 | 数据更新，展示层 | ✅ 预期内 |
| mark_px 来源 | **风控安全距离、网格触发、强平判断**（state.position.mark_px）| 🔴 **交易决策用价** | 🔴 **必须保证 WS 的 mark 价与现 REST 同源可信**；WS 抖动/断线期间不得用脏价下单，需校验+fallback |
| idxPx 来源 | 前端指数价显示 | 展示层 | ✅ |
| OI 来源 | 前端 OI 显示 + OI 锁/判断 | 🟡 趋势/风控若读 OI 需确认 | 🟡 查 OI 在决策链的消费点 |
| candle 来源 | K线图（纯展示）| 展示层 | ✅ |
| WS 断线 | 全部行情展示 | 数据断流 | 🟡 需重连+fallback，绝不裸奔 |

**🔴 最关键**：标记价/最新价既用于展示又用于交易决策（安全距离、网格触发、强平）。**改造必须让交易决策读一个「校验过、可信、断线时降级」的价格**，不能直接裸读 WS 可能滞后的值。规避：WS 数据带时间戳，超过 N 秒陈旧则标记 stale；决策用价优先取「最近一次校验通过」的值 + REST fallback。

### 模块 B（账单）连锁影响

| 改动点 | 下游 | 影响 | 结论 |
|:--|:--|:--|:--|
| 引擎成交 append 记录 | `adjust_records` 缓存、前端调平记录 | 记录实时新增 | ✅ 预期内 |
| adjust-history 改只读缓存 | 前端调平记录展示、bootstrap | 读取更快、不翻页 | ✅ 预期内 |
| 撤销单移入低频任务 | 撤销单展示 | 最多滞后5分钟 | ✅ B方案 |
| 引擎成交处加记录 | **成交/调平交易逻辑** | 🔴 若记录逻辑抛错影响下单 | 🔴 记录必须在 try/except 内，绝不阻断成交/下单流程 |

**🔴 关键**：引擎成交处加记录，**绝不能因为记录逻辑异常而阻断或延迟真实的下单/成交处理**。记录必须在独立 try/except 内，失败只记日志不影响交易。

### 模块 C（缓存层）连锁影响

| 改动点 | 下游 | 影响 | 结论 |
|:--|:--|:--|:--|
| 前端改读缓存 | 前端全部数据展示 | 秒回 | ✅ 预期内 |
| 缓存新鲜度 | 前端数据时效 | 最多滞后 tick 间隔 | 🟡 需接受秒级滞后 |
| 交易决策 vs 展示解耦 | 下单/风控 | 决策仍用真实价，不受展示缓存影响 | ✅ 必须保持解耦 |

## 四、实施顺序（建议分 3 步，每步独立验证）

1. **模块 B（账单三层）**：改动小、直接根治 429+漏记，风险低 → 先做
2. **模块 A（WS）**：改动中、收益最大，但要处理 🔴交易用价 + 断线重连 → 次做
3. **模块 C（统一缓存层）**：前两者就位后的收口 → 最后做

每步走：改代码 → py_compile/node -c → git commit + tag → 隧道推 GitHub → 首尔 pull → 重建重启 → 验证（日志/接口/持仓保留）。

## 五、风险与回滚

- 每次重启前确认持仓（如本次：多39/空47），重启不碰仓位（启动代码只做 init/build_auth/refresh_insts/data_loop）。
- 每个模块独立 tag，可单独回滚。
- 🔴 交易用价与断线 fallback 是最高优先保障，先于任何展示优化。
